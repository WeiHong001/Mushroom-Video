### 3.1 登录与鉴权的正确顺序

1. 请先调用 `GET /api/captcha`，读取 `CaptchaId` 和 `CaptchaUrl`，查看本次验证码图片。
2. 请使用受控测试账号发送 `POST /api/user/login`，JSON 字段为 `phone`、`password`、`captchaId`、`captcha`。注意响应的 `CaptchaId` 与请求的 `captchaId` 大小写不同。
3. 登录成功后，请取 `data.access_token` 的**完整原值**作为 Apifox 环境变量 `x_token`，在需登录接口 Header 中设置 `x-token: {{x_token}}`。
4. 原客户端登录页面没有使用 `token_type` 拼接 token，也没有在提交密码前调用 MD5 或 AES。请您以实际登录响应及后台约定为准，避免因额外编码改变协议。

### 3.2 返回值与错误处理

多数业务接口采用下列外层结构；下例为字段结构说明，不冒充某条接口的实测原文：

```json
{
  "code": 200,
  "message": "",
  "data": {}
}
```

- 请同时检查 HTTP 状态和 JSON 内的 `code`。本次 `/api/user/info` 就是 HTTP 200、业务 `code=403`，表示匿名请求被拒绝。
- 原 `NetCallBack` 将业务码 `1`、`200`、`201`、`302` 进入数据解析分支；页面还可能按自己的业务码判断。这里的业务 302 不等同于 HTTP 重定向。
- DNS 入口直接返回字符串数组；验证码直接返回 `CaptchaId`、`CaptchaUrl` 对象，二者不能套用统一的 `data` 层。
- 网络连接失败、TLS 故障、HTTP 404、业务拒绝和 JSON 解析失败应分别记录；客户端本地码 `1000`、`1001`、`2000` 表示连接/网络/空结果等处理，不冒充服务端状态码。

### 3.3 参数和媒体的易错点

- `vod_id` 指视频内容，`vlog_id` 指短视频内容，`blog_id` 指社区内容；取消收藏时的 `id` 则可能是收藏记录 ID，请勿互换。
- 视频列表使用 `users` 筛选作者，短视频/社区列表使用 `user_id`；名称不同属于原协议。
- 排行 `type` 的客户端值为 `day`、`week`、`month`、`own`；视频搜索关键词为 `wd`，用户搜索为 `name`。
- 详情中 `nubmer` 保留原字段拼写；精品视频列表为大写 `ID`，不要统一改成小写 `id`。
- `play_url` 和封面 URL 是资源地址，内容可能是加密二进制。JSON 接口成功并不代表直接打开资源会显示图片或 m3u8 文本；原 `HttpMyUrlFetcher` 和 `HlsMyPlaylistParser` 负责解密。此前已通过模拟器验证真实封面和加密清单；本次报告未下载真实视频分片。
- 邀请归因 `accessKey` 是该单独业务的派生校验字段，不能作为全站签名；具体构造说明在接口附录中列明。
