## 二、项目现状与迁移必要性

### 2.1 当前实现方式

项目由公司提供的 Android APK 恢复，采用 Java/XML、业务 smali 和部分旧集成 smali 混合构建。部分网络、加解密、播放器适配及自定义控件已有 Java 实现，其余业务仍由 smali 承载。

现有构建支持逐步替换：

- Java 通过仅用于编译期的业务签名 JAR 引用尚未恢复的类型；该 JAR 不得进入运行包。
- 剩余 smali 重新汇编为 DEX，再合入正常构建的 APK。
- 某个功能恢复为源码后，移除其已被替代的 smali，继续与其他未迁移功能共存。

依据请参阅 [现有构建机制](../README.md)、[业务签名生成脚本](../tools/business-abi.gradle) 和 [应用构建配置](../app/build.gradle)。

### 2.2 本次静态盘点

以下为基线提交的文件数量，包含内部类、匿名类及编译器生成类，不代表独立功能数量或待迁移人日：

| 目录或范围 | 盘点结果 | 说明 |
| --- | --- | --- |
| `app/src/main/smali` | 1,068 个 `.smali` 文件 | 业务及基础组件的主要恢复对象 |
| `app/src/main/recovered-libraries` | 2,090 个 `.smali` 文件 | 旧集成、版本或修改情况待核对的库代码 |
| `app/src/main/java` | 30 个 `.java` 文件 | 包含已恢复实现、研究支持代码和资源兼容类，并非均为已迁移业务 |
| `app/src/main` 下的 Kotlin 源码 | 0 个 `.kt` 文件 | 仅指 app 主源码范围；独立诊断模块已有 Kotlin/Compose |
| 原业务页面 | 历史清单列出 38 个 Activity | 清单存在不代表所有业务操作已验证 |
| 原固定资源 ID | 历史 APK 核验记录为 7,141 个 | 迁移中须继续核验，不仅检查源码能否编译 |

`ui/activity`、`ui/frag`、`model`、`adapter`、`api`、`utils` 和 `view` 等目录均有待恢复实现；DataBinding 和路由生成代码须单独识别。启动阶段将按完整类名、功能依赖和运行入口建立正式清单，不按文件数量直接推算工期。

### 2.3 拟达成的效果

1. 提高日常需求定位、调试和修改的可读性，降低直接编辑字节码的成本。
2. 为重要业务建立可重复执行的行为测试，减少依赖人工阅读 smali 的风险。
3. 逐步减少应用对恢复构建步骤的依赖，明确业务源码、生成代码与第三方依赖的边界。
4. 保留可核对的修改和验收记录，便于后续人员维护及交接。

目标是“可维护且经过验证的行为等价实现”，不承诺还原原作者的注释、变量名称或全部源码组织方式。JADX 官方说明反编译可能无法完整还原代码，因此其输出只作为参考，不能直接作为正确性结论。参阅 [JADX 官方说明](https://github.com/skylot/jadx#readme)。

## 四、实施原则与技术路线

### 4.1 小批次与完整调用关系

每批围绕一个独立功能或一组强关联类型开展，不混入无关需求。优先选择依赖较少、输入输出可描述、容易建立回归用例的对象。

范围包括类本身、调用者、内部类、布局、路由、反射入口、序列化约定及配置。遇到依赖闭环或大量编译器生成类型，应将必须同步修改的部分作为同一批次，不强行逐文件替换。

### 4.2 Java/Kotlin 的选择

- 初期优先沿用当前 app 的 Java 编译方式，减少变量；以能清晰表达现有行为、保持调用兼容为准。
- 边界清晰且确有维护收益的模块可采用 Kotlin。当前 app 主模块未应用 Kotlin 编译插件，启用前须核对与已有 Kotlin 版本及构建配置的兼容性，单独记录影响。
- `INSTANCE`、`Companion`、默认参数辅助方法、文件级函数和字段访问器等可能被未迁移 smali 直接调用，须检查实际生成的二进制接口。
- 不要求所有编译器生成类保留相同文件名；若其名称或成员确有外部引用，须保留兼容入口，或在同一批次迁移全部相关调用者。

Kotlin 对 Java 暴露的字段、静态方法和文件类名有明确规则，实施时应核对实际生成结果，参阅 [Kotlin 官方互操作说明](https://kotlinlang.org/docs/java-to-kotlin-interop.html)。

### 4.3 需要保持的契约

1. 类名、父类、接口、字段类型、可见性、静态属性和方法签名。
2. JSON 字段及注解、Parcelable/Serializable 行为、本地存储键与默认值。
3. Activity/Fragment 参数、ARouter 路径、XML 控件类名和反射访问。
4. 回调顺序、线程约束、协程取消、异常传播、空值处理和资源释放。
5. 已记录的 TLS 校验、接口默认方法、媒体监听和图片流回退等兼容修复。

既有差异以 [兼容处理记录](../docs/compatibility.md) 为依据。发现原行为缺陷时，另列问题及预期变化，避免将功能修复与等价迁移混在一起而无法核对。

### 4.4 旧第三方集成的处理

`recovered-libraries` 不统一逐类翻译。每个集成分别核对版本证据、上游修改、制品可用性、资源与清单要求：

1. 匹配制品可确认且兼容时，优先恢复为正式依赖。
2. 有项目定制时，保留修改说明，以符合许可要求的源码或明确适配层承接。
3. 来源、精确版本或修改情况未确认时，保留原实现并登记待确认项，不为“清零”盲目替换。

业务源码恢复与第三方集成退出 smali 的进度分别报告。现有来源与限制请参阅 [第三方依赖与许可清单](../third_party/README.md)。

## 六、单批次执行与交付规范

### 6.1 执行步骤

1. **登记范围。** 记录批次编号、需求、起始提交、类清单、调用者、资源及外部条件。
2. **固定行为。** 对照 smali 和参考 Java，记录输入输出、边界、异常、线程及状态；非平凡逻辑补充有意义的测试。
3. **恢复源码。** 沿用项目结构，不引入无关架构，不以空方法、固定返回值或反编译失败占位代替业务。
4. **核对调用。** 比对未迁移 smali 所需类型、字段与方法；检查内部类及 Kotlin 辅助方法的真实引用。
5. **替换实现。** 仅移除已被源码完整承接的 smali；避免重复打包或遗漏仍被调用的类型。
6. **执行验证。** 按第七节完成构建、测试、APK 核验和相关设备检查，记录实际结果。
7. **复核及回退检查。** 核对范围、证据、风险与撤回方法；高风险批次安排独立复核。
8. **提交交付。** 通过后提交、合入并推送 `dev`，更新记录；失败或阻塞项不标记完成。

- 不重写已共享的历史，不提交设备数据、真实响应、账号、密钥、私有配置及缓存。

启动后拟在 `dev/migration/` 下按批次创建记录，本次不创建虚假的实施报告。每份至少包括：状态、基线提交、完整类名、smali 移除及原因、调用和资源、测试名称、设备及系统版本、构建模式、命令和结果、APK SHA-256、已知限制、复核结论及回退目标。

## 七、验证方案与验收标准

### 7.1 基线与历史证据

仓库已有单元测试、设备测试、APK 核验和历史报告，可供设计迁移验证方案。历史证据包含业务页面、固定资源 ID、诊断隔离和部分播放验证，不代表当前基线的全部场景已在本次重新执行。

请参阅 [业务入口清单](../docs/business-inventory.md)、[历史验证说明](../docs/validation.md)、[APK 核验记录](../docs/apk-verification.json) 和 [诊断模块验证记录](../docs/network-inspector-validation.json)。P0 将重新确认可复现范围，保留迁移前后结果的对应关系。

### 7.2 分层验证

| 层次 | 检查内容 | 合格要求 |
| --- | --- | --- |
| 静态与调用 | 类型、成员、路由、布局、序列化和反射 | 相关引用有实现，调用契约无未处理差异 |
| 行为测试 | 正常、边界、空值、错误、异常和状态变化 | 必须场景通过，相关已有测试无新增失败，差异有解释 |
| 构建 | Debug、测试 APK；重要批次增加研究用 Release | 输出来自本批提交，构建成功不替代业务验收 |
| APK 完整性 | 重复类、缺失 Activity、兼容类、占位泄漏和资源 ID | 无重复运行类、无已知占位泄漏、无缺失的必要类，固定 ID 一致 |
| 设备与集成 | 交互、生命周期、恢复、媒体进度和释放 | 批准场景通过；外部条件不足标记受阻，不计入通过 |
| 发布边界 | Debug 诊断与 Release 隔离、构建和签名配置 | 保持既有隔离；不宣称生产签名、R8 或商店发布已验证 |

可复用 [APK 核验脚本](../tools/verify_apk.py)，但它不能证明全部反射调用及业务操作正确，新增契约仍须针对性验证。必要时使用 [Android 官方 APK Analyzer](https://developer.android.com/studio/debug/apk-analyzer) 比较实际 APK 的 DEX、清单与资源。

### 7.3 启动后可复用的命令

以下为**启动后的执行示例，本次编制计划书不执行这些迁移构建及设备操作**。默认应用模式为 `live`，可重复回归须显式指定 `offline`，避免将真实服务波动引入行为基线。

```powershell
# 在仓库根目录执行，先核对 JDK、SDK 和设备。
.\gradlew.bat --version
.\gradlew.bat :app:assembleDebug :app:testDebugUnitTest :app:assembleDebugAndroidTest -PresearchMode=offline --console=plain
python tools/verify_apk.py app/build/outputs/apk/debug/app-debug.apk

# 阶段门禁或涉及诊断/发布边界时执行。
.\gradlew.bat :core:network-inspector:testDebugUnitTest :app:assembleRelease -PresearchMode=offline --console=plain
python tools/verify_apk.py app/build/outputs/apk/release/app-release.apk
New-Item -ItemType Directory -Path .local/migration -Force | Out-Null
.\gradlew.bat :app:dependencies --configuration releaseRuntimeClasspath --console=plain | Out-File -Encoding utf8 .local/migration/release-dependencies.txt
python tools/verify_inspector_release.py --dependencies .local/migration/release-dependencies.txt
```

执行前须核对脚本当前参数和输出行为。`verify_apk.py` 会更新 `docs/apk-verification.json`，设备脚本也会更新现有报告；应保留基线证据，在批次记录中区分报告对应的模式、APK 和提交，避免覆盖后失去对照。

现有完整页面回归脚本仅允许专用研究模拟器、离线构建，并核对已安装 APK 摘要。执行前确认模拟器无重要数据、安装包与待测产物一致，再按实际序列号操作：

```powershell
# 示例序列号须替换为实际专用模拟器，请勿用于个人日常设备。
$migrationSerial = 'emulator-5580'
adb devices
adb -s $migrationSerial install -r app/build/outputs/apk/debug/app-debug.apk
adb -s $migrationSerial install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
python tools/run_device_validation.py --serial $migrationSerial
```

真机、不同系统版本、媒体和外设验证须按批次另列场景。离线脚本不能替代真实登录、短信、上传、结算及投屏验证；相关验证仅在明确授权和受控条件下开展。

### 7.4 合入与结项门槛

每批合入前应满足：范围完整、必要测试通过、相关已有测试无新增失败、APK 完整性通过、未决风险如实登记、回退目标明确。现存 Lint 等问题先固定为可复核基线，不因当前构建允许通过就忽略新增问题。

最终验收须区分：

1. **批准的业务范围已迁移：** 对照冻结清单逐项验收，剩余 smali 按业务、生成代码、旧集成分别列出，并说明保留原因和维护方式。
2. **全部 smali 退出构建：** 所有剩余运行依赖均由源码、正式依赖或标准生成流程承接；在无 smali 汇编、无业务签名 JAR、无手工合入恢复 DEX 的情况下，构建和约定回归仍通过。

只达到第一项时，不得汇报“全部 smali 已清除”。未经批准，不通过缩小功能清单或删除集成达到完成指标。

## 九、主要风险与处理办法

| 风险 | 可能影响 | 处理与受阻条件 |
| --- | --- | --- |
| 反编译不完整或分支错误 | 编译成功但行为变化 | 对照 smali，补边界和差异测试；关键分支无法解释时保留实现并登记 |
| 二进制、反射或内部类遗漏 | 启动或运行崩溃 | 核对调用及成员，检查 DEX 与真实入口；缺失调用则停止该批合入 |
| Kotlin、协程与生命周期差异 | 取消失效、状态错乱、泄漏 | 复杂闭环成组迁移，补线程、取消和释放检查 |
| JSON、缓存或本地状态变化 | 旧数据不可读或被覆盖 | 保留格式和默认值，以脱敏样本验证；破坏性数据变更移出本计划 |
| 资源 ID、Binding 和生成代码不兼容 | 错页、资源错误、重复类 | 固定 ID 核验，逐项核对生成类，不直接批量重新生成 |
| 旧库版本、定制和许可未确认 | 行为差异或分发依据不足 | 按来源清单核对；材料不足保留实现，记录所需补充材料 |
| 服务、账号或外设缺失 | 部分真实业务无法验收 | 分开记录离线与真实结果，标记受阻，不以模拟结果替代 |
| 现存 Lint 和发布限制 | 研究构建被误认为可生产发布 | 固定既有问题；当前 Release 使用调试签名、未开启 R8，另列发布工作 |
| 测试材料含敏感信息 | 账号和业务数据泄露 | 使用合成或脱敏数据，Git 仅保存必要摘要 |
| 排期低估或与新需求交叉 | 返工及验收困难 | 小批次交付，按试点调整；协调同一功能的新需求与迁移顺序 |

## 十、回退、暂停与变更管理

1. 每批记录可复现的基线提交、模式与条件，利用 Git 保留迁移前实现和 smali 历史。
2. 关键回归、数据兼容或 APK 核验失败时停止合入，不以关闭检查、删除业务或跳过校验绕过问题。
3. 未合入批次保留在需求分支排查；已合入批次通过新的撤销提交回退并复验。普通提交与合并提交的撤销方式按实际历史确认，不强制重置共享分支。
4. 代码回退不自动撤销数据变化、外部操作或生成文件，因此本计划不引入破坏性数据迁移，并使用专用测试环境。
5. 外部条件不足、预算或排期明显偏离时，记录受阻原因、完成范围及可继续事项，提交调整建议。
6. 移除恢复构建步骤安排在收尾批次单独提交，不与最后一批业务重写混成无法拆分的大改动。
